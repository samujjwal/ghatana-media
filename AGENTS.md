# Mandatory Ghatana four-stage, phase-locked review protocol

**Applies to every reviewer, planner, AI agent, and implementer in this repository.** Follow **DISCOVERY → BUILD → DELIVER → ENHANCE** in that order. This is a procedural guard, not a substitute for canonical machine-readable stage, phase, surface, policy, authorization, or proof records. A prompt asking for a broad review does **not** permit work across stages. Do not silently waive these instructions.

## Authoritative definitions — read before acting

- **Kernel development stages:** `samujjwal/ghatana-kernel/docs/spec-driven-development/kernel-development-lifecycle.yaml` — 16 detailed stages from Observe through Evolve. The four names above are **groupings**, not invented replacements for those stage IDs.
- **Discovery/PDP authority:** `samujjwal/ghatana-kernel/docs/product-definition/README.md` — exactly PDP-0 Product Truth, PDP-1 Canonical Domain & Data, PDP-2 Design Language & Interface System, PDP-3 Complete Product Experience. The Experience Explorer is a *projection*, never PDP-4.
- **Phase/closure mechanics:** `samujjwal/ghatana-lifecycle/docs/architecture/PHASE_PROGRAM.md` — repository-local, consumer-authored `PhaseProgram` DAG, and `ClosureUnit = ClosureSurface × Phase`. `PHASE-0…PHASE-7` or other program IDs are **not** aliases for PDP-0…3 or for the four stages.
- **This repository's current authorities:** inspect its actual source manifests, physical/composite surface registry, phase programs/bindings, status records, decision records, and root/nested agent guidance. Current sources override historical plans and generated status projections. Never infer a gate from a Git commit, report heading, checklist, or neighboring repo.

## Non-negotiable campaign gate

1. **Before the first review**, define the exact campaign (repository/product/release scope), inventory every in-scope **physical leaf**, meaningful intermediate **composite**, and root aggregate; identify each applicable PDP-0…3 obligation and owner. An applicable API-only or CLI-only surface is **not** exempt from design/interface or complete-experience definition. An `N/A` must come from an explicit authoritative applicability decision and rationale, never silence or omission.
2. **DISCOVERY-FIRST BARRIER:** no scheduled BUILD campaign work until **ALL** in-scope applicable PDP-0, PDP-1, PDP-2, PDP-3 definitions have reached source-current, validated `DEV_COMPLETE` with **zero outstanding definition tasks**. This applies across the declared campaign, not merely to the first convenient leaf. Unknown, partial, contradictory, stale, or missing status is **not** `DEV_COMPLETE`. Do not narrow the campaign to conceal an incomplete surface.
3. Within Discovery, review and finish the **earliest unfinished PDP phase** first; repair semantic defects at their **owning** phase, then refresh only affected downstream definitions/projections. Source completeness requires stable identities, cross-layer traces, negative cases, applicable interface/experience contracts, current validation and an explicit status record; formatting-only checks are insufficient. **Do not run production implementation, release qualification, native PDP closure, or convergence as a substitute for definition completion.**
4. **At the barrier**, freeze a material-source baseline and retain a phase-by-surface status matrix. A `DEV_COMPLETE` PDP must **not** retain “remaining PDP development tasks.” Classify any reported residual precisely: (a) genuine definition defect → reopen earliest materially impacted PDP and its dependents; (b) implementation/test work → BUILD; (c) owner acceptance/receipt/convergence → parallel PDP closure lane; (d) release/environment work → DELIVER; (e) new opportunity → ENHANCE/new Discovery cycle. Do not inflate an already completed PDP with work from later stages.
5. **After the barrier**, BUILD implementation/verification and **PDP closure/acceptance** may proceed **concurrently** on independent, source-bound units. Closure must use real prerequisite proofs and required independent reviewers/authorities; an agent cannot fabricate clinical/legal/security/qualified signoffs or impersonate a human owner. A closure blocker must not stop unrelated BUILD work, but it **does** stop any DELIVER transition requiring that closure.
6. Do not move to **DELIVER** until applicable PDP closure, BUILD source/test/quality requirements, required owner approvals and environment/release prerequisites are current for exact inputs. Do not move to **ENHANCE** as a substitute for finishing Delivery. Emergency remediation needs a separately recorded, authorized exception/return path; no silent stage skip.

## Reviewer behavior: single-stage, single-phase, finite work

- At the beginning of **each** review, read live repository source/status; select **one macro stage, one concrete phase/substage, one exact surface set, and one source fingerprint**. If the request is ambiguous, choose the **earliest unfinished phase**. If the user explicitly chooses a later phase whose prerequisites fail, provide a **read-only blocker/impact review**, not later-stage implementation or acceptance.
- Inspect **all applicable** physical and composite surfaces at that phase, not only green examples. Resolve phase ownership, currentness, applicability and predecessors. Do not merge `DEV_COMPLETE`, `CLOSED/CURRENT`, `VERIFIED`, `PRODUCTION_QUALIFIED`, and `RELEASE_READY` into a single “done.”
- Findings must be **only for the selected phase**: stable ID, physical/composite owner, what is wrong, exact where, how to fix, predecessor, acceptance test/criterion and resulting next action. Cross-stage discoveries go to a **separate labeled handoff**, not an expanded task backlog for the current phase.
- An unchanged, source-current `DEV_COMPLETE` definition or `CLOSED/CURRENT` closure unit is **skip/reuse**, not repeat-review or rerun. Reopen only on actual affected requirement, meaning, implementation, contract, dependency, approval, or material-input change; propagate impact through declared dependencies, preserving unaffected history. Use bounded parallelism with explicit write/resource ownership.
- Never assert independent review, owner authorization, acceptance receipt, proof, deployment or closure without a genuine source-bound record. Delegated design *recommendations* are not regulated specialist certifications. If unavailable, report exact blocker and lawful next step; do not make up a decision.

## Mandatory review output

Start every review with: **Campaign scope | Source baseline | Macro stage | Exact phase | Physical/composite surface denominator | Prerequisite state | Permitted work**. End with a per-surface phase matrix: **surface ID/type | PDP/phase applicability | source-current status | remaining phase-local tasks (IDs) | blocker/owner | acceptance criteria | next legal action**. Separately state **Discovery barrier status (PASS/FAIL/UNKNOWN)**, **Build lane**, **PDP closure lane**, **Delivery gate**, and the **next allowed phase**. If there are no tasks for a `DEV_COMPLETE` PDP, report **zero**, not invented follow-up work. Claims must distinguish work performed, authoring complete, native closure, and release qualification.

**Never weaken a gate by relabeling a task, moving it into another phase, changing denominators, treating Explorer as authority, or accepting a green aggregate over stale leaves.** Existing repository-specific architecture, security, testing and build instructions continue to apply; this policy adds stage ordering and review scoping, not permission to bypass them.
