## Authoritative contract decisions

### Upload-session contracts: separate two genuinely different representations

The durable Media runtime owns `UploadSession` and HTTP states **OPEN, FINALIZING, COMPLETED, ABORTED, EXPIRED**. Its TypeScript HTTP SDK has already implemented this exact DTO. The earlier exported `UploadSessionSchema` represents a distinct seven-state, different-field legacy client view: **CREATED, UPLOADING, VERIFYING, COMPLETED, FAILED, CANCELLED, EXPIRED**.

**Approved:** no automatic or inferred mapping. Neither `OPEN`→`CREATED`/`UPLOADING`, `FINALIZING`→`VERIFYING`, nor `ABORTED`→`FAILED`/`CANCELLED` is lossless; multiple possible reasons and missing data make such a translation unsound. Maintain both schemas for existing consumers and use the exported `MediaRuntimeUploadStatusSchema` strictly at the canonical wire boundary. Java retains the existing five states. Do not change the current HTTP OpenAPI contract just to match an unrelated compatibility view.

### Stream contracts: one canonical six-state enum

Java runtime and the existing canonical TypeScript SDK already use **OPEN, CONNECTED, DEGRADED, DRAINING, CLOSED, FAILED**. `MediaRuntimeStreamStateSchema` now exports that same vocabulary from the shared types package; the SDK type is an alias. This does not add an RPC, new server, a legacy `StreamSessionSchema`, or live stream qualification.

## Lifecycle outbox and Event Plane source reconciliation (2026-11-21)

**Technical-owner decision:** The Media runtime's lifecycle publisher continues to drain `media_processing_lifecycle_outbox` (V016 plus its lease migration V018). Preserve `media_lifecycle_outbox` (V011) and its existing producer path as a separate event family; do not merge, remap, suppress, or backfill rows between them. This is a source-ownership decision for the current runtime wiring only. It does not establish a complete V011/V016 event-family migration or external delivery admission.

**Source trace:** `MediaRuntime` loads the `MediaLifecycleOutboxSource` provider and drains it at `MediaRuntime#publishLifecycleOutbox` (`launcher/src/main/java/com/ghatana/media/launcher/MediaRuntime.java`); `PostgresqlMediaJobStore.insertOutbox` writes V016 (`providers/aws-postgresql/src/main/java/com/ghatana/media/provider/aws/PostgresqlMediaJobStore.java`); `PostgresqlMediaLifecycleOutboxSource` claims in `(created_at,event_id)` order, calls the publisher, and currently stores only `published_at` in its ACK update (`providers/aws-postgresql/src/main/java/com/ghatana/media/provider/aws/PostgresqlMediaLifecycleOutboxSource.java`). V011 remains implemented independently in `PostgresqlMediaOutboxPublicationSource.append`.

**Event Plane boundary:** The public append response defines `eventId`, `storedEventId`, `streamId`, and `offset` (`../ghatana/services/event-plane/contracts/openapi/event-plane.yaml#/components/schemas/AppendEventResponse`); the current Media publisher validates those four fields and accepts only a nonnegative decimal offset (`launcher/src/main/java/com/ghatana/media/launcher/MediaLifecyclePublisher.java#validateAppendReceipt`). The Event Plane public POST marks replay-safe idempotency as not declared, and its GET exposes exact lookup by tenant header, stream ID, and caller event ID (`../ghatana/services/event-plane/contracts/openapi/event-plane.yaml#/paths/~1api~1v1~1streams~1{streamId}~1events/post`, `.../paths/~1api~1v1~1streams~1{streamId}~1events~1{eventId}/get`). The Event Plane service contract describes bounded lookup and 404 on a completed absent scan (`../ghatana/services/event-plane/service-contract.yaml#requirements/@id=EVT-EXACT-LOOKUP-001`); it does not provide the Media-required current, complete read receipt. `EventRecord.payload` is optional in the OpenAPI schema, and the response contract does not require tenant, query fingerprint, read-authority reference, read version, observation time, or currentness fields. The current publisher boundary also exposes only `void publish(MediaLifecycleEvent)` (`runtime-contracts/src/main/java/com/ghatana/media/runtime/MediaLifecycleEventPublisher.java`), while V016 has no durable receipt/cursor columns.

**Fail-closed disposition:** Keep the relay disabled unless the explicit DEV_ONLY host profile and authenticated destination are configured. A valid 201 may be locally checked against the required four-field append receipt, but it is not an atomically persisted receipt/cursor and does not prove consumption. After a timeout, lost response, incomplete/mismatched receipt, or crash after append but before the Media ACK, exact GET may be attempted only under an independently authorized reader identity; a 404, unavailable, partial, stale, or mismatched result remains UNKNOWN. Never issue an automatic second POST for an ambiguous append. Do not claim a durable cursor, append reconciliation, consumer ACK, effect readback, at-least-once delivery, or production readiness.

**Negative criteria:** (1) no treating HTTP 201 or `published_at` alone as a consumed/effected event; (2) no retry after an ambiguous append without a versioned Event Plane replay guarantee; (3) no treating GET 404 as proof of non-commit without a current complete receipt; (4) no accepting a lookup that cannot bind trusted tenant, stream, caller ID, stable stored UUID, event version, and canonical payload fingerprint; (5) no synthesized Event Plane partition field; use only the trusted tenant scope plus returned `streamId` and monotonic `offset` where the public contract proves those identities; (6) no credential or row flow from V011 into V016 or vice versa.

**Smallest external source decisions required:** The Shared Event Plane owner must reconcile the public no-retry append declaration with `EVT-EXACT-LOOKUP-001`, publish a current/complete typed lookup receipt (including trusted tenant and enough event data to validate the canonical payload fingerprint), and define the reader authority and exact replay/absence semantics. ### Addendum — Event Plane owner source confirmation (2026-11-21)

The preceding audit captured the public OpenAPI mismatch before the Event Plane owner/source review. Current `EventPlaneHttpHandler.appendEvent` requires `Idempotency-Key`; `IdempotentKafkaEventLogStore` binds the caller UUID, per-tenant key and canonical content fingerprint, returns the original offset/receipt for an exact replay, and conflicts on key/content reuse. The Kafka adapter maps one tenant to one topic partition, uses transactional append and read-committed replay. Exact lookup by trusted tenant, logical stream and caller event ID returns the stable stored UUID, caller ID, stream, payload/headers/idempotency key and tenant-wide offset; a complete retained absence is 404, while indeterminate and bounded lookup outcomes are 503 and 422. These implementation facts do not erase the stale public OpenAPI declaration; the Shared owner is reconciling it and adding `storedEventId` to the uniform receipt.

**Media implementation rule after source confirmation:** Derive a stable bounded idempotency key from `(trusted tenant_id, V016 event_id)` and repeat the exact immutable request only after the exact lookup returns complete 404. A 200 lookup is accepted only when tenant, caller ID, stored UUID, logical stream, event type/version, idempotency key, timestamp and canonical payload all match the V016 row. A 503, 422, missing/incomplete field, mismatch, or failed reader authorization remains durable `OUTCOME_UNKNOWN` and is never resent. Use the trusted tenant as the physical cursor partition key and persist the Event Plane's monotonic tenant-wide offset and returned `streamId` with the per-event append receipt in the same V016 ACK transaction; do not invent a partition identifier or call this a consumer/effect cursor. Keep V011 physically and semantically separate.

### Addendum — prior-attempt reconciliation fence (2026-11-21)

The V016 claim path now requires exact readback before append whenever the durable attempt count is nonzero, as well as when reclaiming an expired lease.
